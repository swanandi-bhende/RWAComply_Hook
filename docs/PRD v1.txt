1. Executive Summary
1.1 What is RWAComply?
RWAComply is a compliance-aware trading infrastructure layer built on Uniswap v4.
It allows issuers of tokenized real-world assets (RWAs) to create purchase policies that apply to individual humans rather than individual wallets.
The system uses World ID to establish that a participant is a unique human. It then allows that participant to associate multiple wallets with one privacy-preserving allocation identity.
When the participant purchases an RWA token through a supported RWAComply trading route, the Uniswap v4 hook checks how much that human has already purchased.
If the purchase would exceed the issuer's configured limit, the transaction is rejected onchain.
1.2 The problem
Most blockchain applications identify users through wallet addresses.
A single person can create multiple wallets and use each one independently.
For example, suppose an issuer wants to distribute a tokenized treasury product with a maximum retail purchase limit of $1,000 per person.
Alice creates three wallets:
* Wallet A purchases $700.
* Wallet B purchases $500.
* Wallet C purchases $400.
If the system only tracks wallet-level purchases, all three transactions may be accepted.
Alice has effectively purchased $1,600 even though the issuer intended to limit her to $1,000.
The problem is not necessarily that the issuer has no purchase limit. The problem is that the limit is attached to an address rather than a person.
1.3 The solution
RWAComply introduces a shared purchase allocation for each verified human.
Alice verifies through World ID and establishes an RWAComply session.
She then links Wallet A and Wallet B to the same issuer-scoped allocation identity.
The system records:
Wallet
	Purchase
	Shared spend
	Alice — Wallet A
	$700
	$700
	Alice — Wallet B
	$500 attempted
	$1,200 attempted
	The second purchase is rejected because it would exceed the $1,000 allocation.
Alice can still use Wallet B to purchase $300 or less.
Bob, who has a different verified-human allocation identity, receives a separate $1,000 allocation.
1.4 Product promise
One human. Multiple wallets. One shared purchase budget.
1.5 Core product distinction
RWAComply is not:
* A KYC provider.
* A complete regulatory compliance platform.
* A token issuance platform.
* A general-purpose identity wallet.
* A frontend-only wallet restriction.
* A system that can automatically detect every wallet belonging to a person.
It is an identity-assisted allocation enforcement system.
World ID establishes uniqueness and session continuity. RWAComply connects authorized wallets to a shared allocation identity. Uniswap v4 enforces the purchase policy during supported swaps.
1.6 Target outcome
The first release must demonstrate the following complete flow:
1. An issuer creates a $1,000 purchase policy.
2. Alice connects Wallet A.
3. Alice completes World ID Proof of Human verification.
4. Wallet A is associated with Alice's allocation identity.
5. Alice purchases $700 of an RWA token.
6. Alice connects Wallet B.
7. Alice proves that she belongs to the existing World ID session.
8. Wallet B is associated with the same allocation identity.
9. Wallet B attempts to purchase $500.
10. The Uniswap v4 hook rejects the transaction.
11. Wallet B purchases $200 successfully.
12. Bob verifies separately and can purchase from his own allocation.
The purchase restriction must be enforced by smart contracts, not just by the backend or frontend.

3. Problem Statement
3.1 Primary problem
RWA issuers need to enforce purchase limits at the level of an individual investor.
Wallet addresses are not reliable representations of individual investors because one person can control multiple wallets.
If purchase limits are applied independently to each wallet, users can bypass them by splitting purchases across addresses.
3.2 Why this matters
Tokenized real-world assets may have issuer-defined distribution rules.
Examples include:
* Maximum retail allocation per investor.
* Maximum amount of a particular offering that one investor may acquire.
* Different purchase limits for retail and institutional investors.
* Restricted participation during a particular offering period.
* Issuer-defined purchase eligibility.
A wallet-based limit cannot reliably represent a human-level limit.
3.3 Problems RWAComply V2 addresses
Problem 1: Multiple wallets
One human can create or control multiple wallets.
Solution: Allow multiple wallets to be associated with one verified-human allocation identity.
Problem 2: Independent purchase counters
A separate counter for every wallet allows cumulative purchases to exceed the intended limit.
Solution: Store spending against the shared allocation identity.
Problem 3: Frontend-only restrictions
A frontend can prevent a user from clicking a purchase button, but the user may interact directly with a contract.
Solution: Enforce purchase limits inside the Uniswap v4 hook.
Problem 4: Unclear issuer policies
Different pools may have different purchase rules, even when they belong to the same issuer or offering.
Solution: Introduce allocation groups that allow multiple pools to share one purchase budget.
Problem 5: Unnecessary identity disclosure
A normal identity system may require users to reveal personal information.
Solution: Use World ID Proof of Human and session proofs without collecting names, government IDs or other personal information for the core feature.
Problem 6: Limited transparency
Users may not understand why a transaction is rejected or how much allocation remains.
Solution: Display the active policy, cumulative spending, remaining budget and transaction result.
3.4 What is not solved?
RWAComply V2 does not automatically solve:
* A person using different World ID identities.
* A person purchasing assets outside RWAComply-supported routes.
* Transfers of RWA tokens between wallets after purchase.
* Purchases on unrelated chains.
* KYC or AML requirements.
* Accreditation or residency checks.
* Fraudulent issuers.
* Incorrect issuer-provided asset information.
* Legal compliance in every jurisdiction.
These limitations must be clearly documented.

7. Core Product Concepts
This section defines the terms used throughout the product.
7.1 World ID
World ID is used to verify that a participant is a unique human.
RWAComply uses Proof of Human for the main retail flow.
World ID does not tell RWAComply the participant's legal name, nationality, residency or accreditation status.
7.2 World ID session
A session allows RWAComply to recognize that a later interaction belongs to the same World ID holder as an earlier interaction.
This is important because the system must recognize the same human when they connect another wallet.
The product must not assume that a user can repeatedly submit the same one-time uniqueness proof and receive a reusable nullifier.
Instead:
1. The user completes an initial uniqueness proof.
2. The user establishes an RWAComply session.
3. The application stores the session reference securely.
4. The user can later prove continuity with that session.
5. The backend verifies the session proof.
6. The backend associates the newly connected wallet with the existing allocation identity.
The World ID session identifier must remain offchain.
Official technical reference: https://worldcoin.github.io/world-id-protocol/world-id-4-specs/
7.3 Allocation identity
An allocation identity is a pseudonymous identifier representing one verified human within a particular issuer's allocation system.
It is not a wallet address.
It is not a World ID nullifier.
It is not a publicly identifiable real-world identity.
It is an application-level identifier used to associate wallets with one spending record.
For privacy, the allocation identity should be scoped to an issuer rather than globally reused across every issuer.
Example:
* Alice's allocation identity for Issuer A: humanKeyA
* Alice's allocation identity for Issuer B: humanKeyB
Both represent the same World ID holder, but the identifiers are different.
This prevents the onchain system from automatically exposing that the same person participates in multiple unrelated issuers' offerings.
7.4 Wallet registration
Wallet registration connects a wallet address to an allocation identity.
A wallet must be registered before it can use the retail purchase route.
A user may register multiple wallets.
A wallet must not be silently reassigned to another allocation identity.
7.5 Allocation policy
An allocation policy defines how much a verified human may purchase.
Example:
* Issuer: Treasury Issuer A.
* Offering: Treasury Basket 2026.
* Maximum purchase: $1,000.
* Quote currency: USDC.
* Allocation period: November 2026.
* Allocation group: TREASURY-2026-01.
7.6 Allocation group
An allocation group connects multiple pools to one shared spending counter.
Example:
Pool
	Allocation group
	Treasury Token A / USDC
	TREASURY-2026-01
	Treasury Token B / USDC
	TREASURY-2026-01
	Treasury Token C / USDC
	TREASURY-2026-01
	All three pools use the same purchase budget for the same human.
7.7 Cumulative spend
Cumulative spend is the total gross amount a human has purchased through supported RWAComply routes during the applicable allocation period.
For the MVP:
* Spending is measured in USDC.
* Purchases count toward the limit.
* Selling does not restore the allocation.
* Failed transactions do not count.
* Unsupported routes do not count.
* The counter is shared across pools in the same allocation group.
7.8 Remaining allocation
Remaining allocation is:
Remaining allocation = Maximum allocation - Cumulative spend
The remaining amount cannot be negative.

8. Main Product Workflows
8.1 Workflow A — Issuer creates an offering
Actor: Issuer administrator
Precondition: The issuer has been authorized to create policies.
Steps:
1. Issuer opens the issuer dashboard.
2. Issuer connects the authorized wallet.
3. Issuer selects "Create Offering".
4. Issuer enters the offering name.
5. Issuer enters the RWA token address.
6. Issuer selects USDC as the quote currency.
7. Issuer enters the maximum purchase amount per verified human.
8. Issuer defines the allocation period.
9. Issuer creates an allocation group.
10. Issuer selects the pools that belong to the group.
11. Issuer reviews the policy.
12. Issuer confirms the transaction.
13. The policy registry stores the configuration.
14. The frontend publishes the public offering information to Arkiv.
15. The offering appears in the investor directory.
Expected result:
The offering is visible, its policy is active and all registered pools use the same allocation group.
Failure cases:
* Issuer is not authorized.
* Invalid token address.
* Invalid quote token.
* Maximum allocation is zero.
* Allocation period is invalid.
* Pool is not configured with the expected hook.
* Allocation group already exists with conflicting parameters.
* Arkiv publication fails.
If Arkiv publication fails, the onchain policy should remain valid. The application should display a publication error and allow the issuer to retry.
8.2 Workflow B — First wallet verification
Actor: Retail investor
Precondition: The investor has a connected wallet and an active offering.
Steps:
1. Alice opens the offering.
2. Alice connects Wallet A.
3. The frontend checks whether Wallet A is already registered.
4. If it is not registered, the frontend displays the verification requirement.
5. Alice selects "Verify with World ID".
6. IDKit starts the Proof of Human flow.
7. Alice completes the verification.
8. The application receives the proof response.
9. The frontend sends the proof to the backend.
10. The backend verifies the proof with World.
11. The application establishes an RWAComply session.
12. The backend creates or retrieves Alice's issuer-scoped allocation identity.
13. The backend issues a wallet-registration authorization.
14. Alice registers Wallet A onchain.
15. The contract verifies the backend authorization.
16. The contract stores Wallet A's allocation identity.
17. The frontend confirms registration.
18. The dashboard displays the allocation limit and remaining amount.
Expected result:
Wallet A is linked to Alice's allocation identity.
Important requirements:
* The World verification secret must never be exposed in the browser.
* The backend must verify the proof.
* The frontend must not treat an unverified response as authorization.
* The session identifier must not be published onchain.
* The wallet registration must be protected against replay.
8.3 Workflow C — Linking a second wallet
Actor: Retail investor
Precondition: Alice has already completed the initial World ID verification and has an existing session.
Steps:
1. Alice switches from Wallet A to Wallet B.
2. The frontend detects that Wallet B is not registered.
3. Alice selects "Link another wallet".
4. The application requests a World ID session proof.
5. The authenticator proves continuity with the existing session.
6. The frontend sends the proof to the backend.
7. The backend verifies the proof.
8. The backend confirms that the proof belongs to Alice's existing session.
9. The backend retrieves Alice's issuer-scoped allocation identity.
10. The backend issues a registration authorization for Wallet B.
11. Alice registers Wallet B onchain.
12. The contract records the same allocation identity for Wallet B.
13. The dashboard displays both wallets under the same allocation.
Expected result:
Wallet A and Wallet B resolve to the same allocation identity.
Important:
The application must not use a new independent identity for Wallet B if the session proof succeeds.
Failure cases:
* No existing session.
* Session proof is invalid.
* Session proof belongs to another session.
* Session has expired or is unavailable.
* Backend cannot find the session mapping.
* Wallet registration authorization has expired.
* Wallet is already registered to another allocation identity.
If the session cannot be recovered, the application must not silently create a new allocation identity. It should explain the recovery limitation.
8.4 Workflow D — Successful purchase
Actor: Retail investor
Precondition:
* Wallet is registered.
* Allocation policy is active.
* Pool belongs to the correct allocation group.
* Wallet has sufficient USDC.
* Wallet has approved the supported executor to spend the required USDC.
Example:
* Maximum allocation: $1,000.
* Current spend: $0.
* Requested purchase: $700.
Steps:
1. Alice selects the offering.
2. Alice enters $700.
3. The frontend reads her current allocation.
4. The frontend displays $1,000 available.
5. The frontend requests a quote.
6. Alice confirms the purchase.
7. The wallet signs or authorizes the trade intent as required by the executor.
8. The executor verifies the trade request.
9. The executor calls the Uniswap v4 PoolManager through the supported route.
10. The hook receives the swap callback.
11. The hook verifies the executor.
12. The hook validates the signed trade authorization.
13. The hook identifies the registered wallet.
14. The hook retrieves the allocation identity.
15. The hook retrieves the relevant allocation group and period.
16. The hook reads the current cumulative spend.
17. The hook checks whether the requested purchase fits within the remaining allocation.
18. The hook updates cumulative spend.
19. The Uniswap swap executes.
20. The transaction completes.
21. The frontend reads the updated spending record.
22. The frontend displays the successful purchase and remaining allocation.
Expected result:
Alice spends $700 and has $300 remaining.
Atomicity requirement:
If any part of the transaction fails after the hook updates the spend counter, the complete transaction must revert. The spend update must not remain after a failed swap.
8.5 Workflow E — Rejected purchase through a second wallet
Actor: Retail investor
Precondition:
* Wallet A and Wallet B are registered to the same allocation identity.
* Maximum allocation is $1,000.
* Wallet A has already purchased $700.
Steps:
1. Alice connects Wallet B.
2. The frontend retrieves the shared allocation record.
3. The frontend displays $300 remaining.
4. Alice attempts to purchase $500.
5. The executor submits the transaction.
6. The hook reads the same allocation identity used by Wallet A.
7. The hook reads cumulative spend of $700.
8. The hook calculates the new total: $1,200.
9. The hook detects that the maximum is $1,000.
10. The hook reverts the transaction.
11. The frontend displays the rejection reason.
Expected result:
No tokens are purchased, and the spending counter remains $700.
The rejection must happen onchain.
8.6 Workflow F — Purchase from a different human
Actor: Bob
Precondition: Bob has completed his own World ID verification.
Steps:
1. Bob connects his wallet.
2. Bob completes Proof of Human.
3. Bob receives a separate allocation identity.
4. Bob registers his wallet.
5. Bob purchases $900.
6. The hook checks Bob's spending record.
7. The purchase is accepted.
8. Bob has $100 remaining.
Expected result:
Alice's purchases do not affect Bob's allocation.
8.7 Workflow G — Multiple pools share an allocation
Actor: Retail investor
Example:
* Pool A: Treasury Token A / USDC.
* Pool B: Treasury Token B / USDC.
* Both pools use the same allocation group.
* Maximum allocation: $1,000.
Alice:
* Purchases $600 through Pool A.
* Attempts $500 through Pool B.
Expected result:
The second purchase is rejected because the shared spend would become $1,100.
The allocation must not be stored independently for each pool.
8.8 Workflow H — Issuer pauses an offering
Actor: Issuer administrator
Steps:
1. Issuer opens the dashboard.
2. Issuer selects an active offering.
3. Issuer selects "Pause".
4. Issuer confirms the transaction.
5. The policy registry marks the offering as paused.
6. The hook rejects further purchases for that offering.
Expected result:
No new purchases are accepted until the issuer resumes the offering.
Existing spending records must remain unchanged.

9. Product Rules and Business Logic
9.1 Purchase-limit calculation
The primary rule is:
New cumulative spend = Existing cumulative spend + Requested purchase
A purchase is allowed only when:
New cumulative spend <= Maximum allocation
Equivalent validation:
Requested purchase <= Maximum allocation - Existing cumulative spend
The contract must use safe integer arithmetic and must not rely on frontend calculations.
9.2 Spending denomination
For the MVP, all purchase budgets are denominated in USDC.
Reasons:
* USDC is a familiar stable-value quote asset.
* It avoids introducing multiple price feeds.
* It makes spending records easy to understand.
* It simplifies cross-pool accounting.
* It avoids currency conversion errors in the first implementation.
All pools sharing an allocation group must use the same quote-token address and denomination.
The application must handle USDC's token decimals correctly.
The contract stores the smallest token unit, not a floating-point dollar amount.
For example:
$1,000 USDC is represented as 1,000 × 10^6 units for a six-decimal USDC token.
9.3 Gross purchase accounting
The system counts gross purchases.
If Alice purchases $700 and later sells $200, her cumulative purchase spend remains $700.
Reason:
Allowing a sale to restore allocation would let users repeatedly buy and sell to bypass the intended gross purchase limit.
9.4 Failed transactions
A failed transaction does not count toward the allocation.
The accounting update and the swap must be atomic.
If the swap reverts, the allocation update must also revert.
9.5 Exact-input purchases only
The MVP supports exact-input swaps.
The investor specifies the amount of USDC they want to spend.
The system does not support exact-output purchases in the first release.
This makes the amount used for purchase accounting easier to determine.
The hook must reject unsupported swap types.
9.6 Single-pool and multi-pool behavior
A policy may apply to one or multiple pools.
Every pool sharing the same allocation group must:
* Use the same chain.
* Use the same quote-token address.
* Reference the same allocation group.
* Use a compatible policy period.
* Use the approved RWAComply hook and supported executor.
A pool cannot silently change allocation groups after trading has started.
9.7 Allocation periods
A policy may have a start time and an end time.
For the MVP, a new allocation period receives a new periodId.
Example:
* November offering: periodId = 1.
* December offering: periodId = 2.
Spending from November does not automatically carry into December unless the issuer deliberately configures a continuing allocation group and period.
The frontend must display the active period.
9.8 Policy updates
The issuer may update policy parameters according to its permissions.
Examples:
* Increase the maximum allocation.
* Decrease the maximum allocation.
* Pause the offering.
* Resume the offering.
* Change the offering's end date if permitted.
Rules:
1. The issuer cannot change the quote token of an active allocation group.
2. The issuer cannot reset spending by changing the policy version.
3. A new policy version must not erase existing spending.
4. The issuer cannot reduce the cap below the amount already spent.
5. Old trade authorizations must not remain valid after a policy update if they were issued for an earlier policy version.
6. All updates must emit events.
9.9 Institutional users
Institutional access remains separate from World ID Proof of Human.
World ID does not prove that a user is an accredited investor or an institution.
For V2:
* Retail users use World ID and the shared allocation model.
* Institutional wallets are approved through an issuer-controlled allowlist.
* Institutional limits are configured separately.
* Institutional access must not automatically bypass every policy.
* The issuer decides whether an institutional wallet has a different cap or an unrestricted allocation.
The initial demo focuses on retail users.
9.10 Token transfers
The MVP enforces purchases through supported RWAComply trading routes.
It does not guarantee that a person cannot acquire the RWA token through:
* A direct transfer.
* An unrelated exchange.
* Another Uniswap pool.
* Another chain.
* A different protocol.
If an issuer requires ownership-level restrictions, the RWA token itself must implement compatible transfer controls.
The product must not claim to enforce total ownership across every wallet.

10. Technical Architecture
10.1 Architecture overview
The system contains six main layers.
Layer 1 — Frontend
Responsibilities:
* Wallet connection.
* Offering discovery.
* World ID verification.
* Wallet linking.
* Allocation display.
* Purchase interface.
* Issuer dashboard.
* Transaction history.
Layer 2 — World ID integration
Responsibilities:
* Start Proof of Human.
* Create a session.
* Request session proofs.
* Provide verification results.
Layer 3 — Backend
Responsibilities:
* Verify World ID proofs.
* Maintain session-to-allocation mappings.
* Generate issuer-scoped allocation identities.
* Issue wallet-registration attestations.
* Verify wallet-registration requests.
* Provide read APIs for the frontend.
* Maintain operational logs without storing unnecessary identity data.
Layer 4 — Onchain identity and policy registry
Responsibilities:
* Store wallet-to-allocation mappings.
* Store issuer policies.
* Store allocation groups.
* Store cumulative spend.
* Validate backend attestations.
* Enforce policy permissions.
Layer 5 — Uniswap v4 execution
Responsibilities:
* Authenticate supported swap routes.
* Validate the signed trade intent.
* Check allocation availability.
* Update cumulative spending.
* Allow or reject swaps.
Layer 6 — Arkiv
Responsibilities:
* Store public offering metadata.
* Allow the frontend to query available offerings.
* Store issuer-published policy descriptions and references.
* Provide an externally queryable offering directory.
Arkiv does not store World ID session identifiers, wallet-to-human mappings or spending counters.
10.2 High-level flow
1. User connects a wallet.
2. User completes World ID verification.
3. Backend verifies the proof.
4. Backend creates or retrieves the issuer-scoped allocation identity.
5. User registers the wallet onchain.
6. User requests a purchase.
7. Trusted executor validates the wallet and trade intent.
8. Uniswap v4 calls the hook.
9. Hook retrieves the wallet's allocation identity.
10. Hook checks the allocation policy.
11. Hook updates cumulative spend.
12. Swap executes or reverts.
13. Frontend displays the final result.

11. World ID and Identity Architecture
11.1 Selected credential
Use World ID Proof of Human.
Reason:
The product needs to establish that a participant is a unique human.
It does not need to collect a passport, government ID or legal name.
11.2 Initial verification
The first verification establishes the user's RWAComply session.
The backend must:
1. Receive the proof from the frontend.
2. Validate the request and expected application configuration.
3. Verify the proof through the official World verification flow.
4. Confirm that the proof is valid for the intended action.
5. Create or retrieve the session mapping.
6. Associate the session with an issuer-scoped allocation identity.
The backend must not trust the frontend's claim that verification succeeded.
11.3 Session-based wallet linking
The second wallet uses a session proof.
The backend must confirm that the session proof belongs to the same session as the initial verification.
If it does, the backend can retrieve the existing allocation identity.
The second wallet is then registered against that identity.
11.4 Issuer-scoped allocation identities
A user's allocation identity should be scoped to an issuer.
The backend maintains a relationship conceptually similar to:
World session → Issuer scope → Allocation identity
The onchain contract receives only the opaque allocation identity.
The same user should not automatically have one publicly visible identity across unrelated issuers.
11.5 Session storage
The backend may store the session identifier because it needs it for subsequent session proofs.
Requirements:
* Store it server-side.
* Encrypt it at rest.
* Restrict access.
* Do not expose it through public APIs.
* Do not publish it to Arkiv.
* Do not emit it in smart contract events.
* Do not include it in transaction calldata.
* Do not use it as a public wallet identifier.
11.6 Wallet registration authorization
The backend issues an authorization that binds:
* Wallet address.
* Allocation identity.
* Chain ID.
* Registry contract address.
* Authorization expiry.
* Registration nonce.
* Relevant issuer scope.
The registration contract verifies the backend signature.
The simplest MVP registration flow requires the wallet itself to submit the registration transaction. This proves that the caller controls that wallet.
If a relayer is introduced later, the wallet must provide an additional wallet signature.
11.7 Backend signer
The backend signer is a trusted attestor.
It must:
* Be stored in a secure server environment.
* Never be exposed in frontend variables.
* Be configurable through deployment settings.
* Support rotation.
* Have restricted authority.
* Be monitored for misuse.
The contract should allow an authorized administrator to rotate the signer.
11.8 Session expiry and recovery
Session expiry or loss must not automatically create a new allocation identity.
Otherwise, a user could potentially receive a fresh spending record.
For the MVP:
* If the session is available, use it.
* If the session proof fails, show an error.
* If the session is lost, require a documented recovery process.
* Do not automatically reset the user's cumulative spend.
* Do not allow an administrator to erase a user's spending history.
Full decentralized recovery is outside the MVP.
11.9 World ID failure states
The application must handle:
* User cancels verification.
* User does not have the required credential.
* Verification proof is invalid.
* Verification proof is expired.
* Verification service is unavailable.
* Session creation fails.
* Session proof fails.
* Backend verification fails.
* Backend signer is unavailable.
In all such cases, the user must not receive an unverified allocation registration.

12.5 RWAComplyHook
Purpose:
Enforce the policy during Uniswap v4 swaps.
The primary enforcement point is beforeSwap.
Required checks
1. The caller must be the expected PoolManager.
2. The pool must be registered.
3. The policy must be active.
4. The swap must use an approved executor.
5. The trade intent must be valid.
6. The wallet must be registered.
7. The wallet must not be revoked.
8. The allocation identity must exist.
9. The swap must be exact-input.
10. The input currency must be the configured quote token.
11. The amount must be positive and within supported limits.
12. The policy period must be active.
13. The trade authorization must match the policy version.
14. The purchase must fit within the remaining allocation.
15. The trade authorization nonce must not have been used.
If any required check fails, the swap must revert.
12.6 Trusted executor
The hook must not trust an arbitrary wallet address supplied in hookData.
In Uniswap v4, the hook's sender parameter represents the initial caller to the PoolManager. It may be a router or executor rather than the end user's wallet.
The hook therefore needs a defined, trusted route.
The MVP should use a dedicated executor.
Responsibilities:
* Receive the user's purchase request.
* Validate the wallet's authorization.
* Ensure the correct wallet funds the purchase.
* Call the PoolManager.
* Pass the signed trade intent to the hook.
* Ensure the output is delivered to the authorized recipient.
* Settle the required token balances.
* Prevent unauthorized route parameters.
The hook must independently verify the important authorization fields rather than trusting arbitrary hook data.

12.8 Swap amount accounting
The MVP supports exact-input purchases using USDC.
The hook should determine the input token and amount from the actual Uniswap swap parameters.
It must confirm:
* The swap is exact-input.
* USDC is the input currency.
* The pool is registered to the relevant allocation group.
* The amount matches the signed trade authorization.
The hook should not calculate spending from a user-supplied frontend value.
The amount recorded must match the amount actually specified for the supported purchase.
12.9 Atomic spending update
The hook may update the spending counter during the swap execution path.
If the swap later fails, the entire EVM transaction must revert, including the spending update.
There must be no separate offchain step that permanently records a purchase before the swap has succeeded.

17. Security and Threat Model
Security is a core product requirement because the system controls access to financial purchases.
17.1 Threat: Multiple wallets
Attack: A person creates multiple wallets to bypass the purchase cap.
Protection: Wallets linked through the same World ID session resolve to one allocation identity.
17.2 Threat: Forged wallet association
Attack: An attacker attempts to register another person's wallet against their own allocation identity.
Protection:
* Backend verifies World ID session continuity.
* Backend issues an authorization for the specific wallet.
* The wallet must submit the registration transaction or provide a valid wallet signature.
* Contract checks the backend signature.
17.3 Threat: Replaying registration authorization
Attack: An attacker reuses an old registration signature.
Protection:
* Nonce.
* Expiry.
* Chain ID.
* Contract address.
* Wallet binding.
* Signature verification.
17.4 Threat: Replaying trade authorization
Attack: A user reuses an old signed purchase intent.
Protection:
* Trade nonce.
* Expiry.
* Exact input amount.
* Pool binding.
* Policy binding.
* Allocation-group binding.
* Executor binding.
* Nonce consumption.
17.5 Threat: Forged hook data
Attack: A caller supplies another wallet address through hookData.
Protection:
* Only the trusted executor may call the supported route.
* Hook verifies the signed trade intent.
* Wallet must be registered.
* Executor ensures the correct input funding and output recipient.
17.6 Threat: Unauthorized router
Attack: An attacker calls the PoolManager directly and attempts to bypass the executor.
Protection:
The hook rejects unsupported execution routes.
17.7 Threat: Spending counter reset
Attack: A user attempts to reset their spending by changing policy versions or registering another wallet.
Protection:
* Spending is keyed by allocation identity, allocation group and period.
* Policy versions do not reset spending.
* Wallets cannot be freely reassigned.
* Revocation does not erase historical spending.
17.8 Threat: Selling and repurchasing
Attack: A user sells tokens and expects their purchase budget to reset.
Protection:
The system tracks gross purchases. Selling does not restore the allocation.
17.9 Threat: Issuer changes policy maliciously
Attack: An issuer changes the policy to erase previous spending or bypass restrictions.
Protection:
* Policy changes are permissioned.
* Spending remains independent of policy version.
* Policy changes emit events.
* Cap cannot be reduced below already-spent amounts.
* Policy changes must be visible in the frontend.
17.10 Threat: Backend signer compromise
Attack: An attacker obtains the backend signing key and issues false wallet registrations.
Protection:
* Secure key storage.
* Restricted signer permissions.
* Monitoring.
* Key rotation.
* Administrative pause.
* Short authorization expiry.
* Issuer-scoped allocation identities.
The backend signer remains a trust assumption in the MVP.
17.11 Threat: World verification service unavailable
Attack or failure: The verification provider is unavailable.
Protection:
New registrations and wallet linking are paused until verification works.
Already registered wallets may continue trading if their onchain registration and policies remain valid.
The system must not bypass verification to preserve availability.
17.12 Threat: Arkiv data manipulation
Attack: An attacker publishes misleading offering metadata.
Protection:
* Issuer ownership is checked.
* Issuer wallet is displayed.
* Onchain policy is authoritative.
* Token and pool addresses are validated against onchain records.
* Stale or inconsistent metadata is flagged.
17.13 Threat: Oracle manipulation
The MVP does not rely on an oracle for purchase-limit calculations.
If the existing volatility-fee mechanism remains enabled, it must have separate stale-price and invalid-feed protections.
17.14 Threat: Reentrancy and accounting inconsistency
The hook and executor must be reviewed for:
* Reentrancy.
* Repeated callbacks.
* Incorrect nonce consumption.
* Incorrect spending updates.
* Token settlement failures.
* Partial execution.
* Invalid balance assumptions.
The hook should not hold user funds unnecessarily.
17.15 Privacy requirements
* Do not publish World ID session IDs.
* Do not publish World ID proofs.
* Do not expose personal information.
* Do not reuse a global allocation identity across unrelated issuers.
* Do not emit sensitive data in events.
* Explain that linked wallets share an allocation record.
* Explain that allocation activity within an issuer's scope is linkable by the application.

FR-ID-03: The application must establish an RWAComply session after successful initial verification.
FR-ID-04: The application must support session proofs for linking additional wallets.
FR-ID-05: The backend must associate session proofs with the correct issuer-scoped allocation identity.
FR-ID-06: The session identifier must remain offchain.
FR-ID-07: Invalid or expired proofs must not create wallet registrations.
19.2 Wallet requirements
FR-W-01: A wallet must be registered before retail trading.
FR-W-02: A user may link multiple wallets.
FR-W-03: Multiple wallets linked to the same allocation identity must share spending.
FR-W-04: A wallet cannot be silently reassigned to another identity.
FR-W-05: Revoked wallets cannot execute new purchases.
FR-W-06: Revocation must not erase historical spending.
19.3 Policy requirements
FR-P-01: Authorized issuers can create policies.
FR-P-02: A policy must define a maximum allocation.
FR-P-03: A policy must define a quote token.
FR-P-04: A policy must define an allocation period.
FR-P-05: A policy must define an allocation group.
FR-P-06: A policy can be paused and resumed by authorized actors.
FR-P-07: Policy updates must increment the version.
FR-P-08: Policy updates must not reset spending.
FR-P-09: A policy must be associated with registered pools.
19.4 Trading requirements
FR-T-01: The system must support exact-input USDC purchases.
FR-T-02: The system must reject unregistered wallets.
FR-T-03: The system must reject unauthorized executors.
FR-T-04: The system must validate the signed trade intent.
FR-T-05: The system must check the shared allocation balance.
FR-T-06: The system must reject purchases that exceed the limit.
FR-T-07: The system must record successful purchases.
FR-T-08: Failed swaps must not permanently update spending.
FR-T-09: Multiple pools in the same allocation group must share the same spending record.
FR-T-10: Selling tokens must not restore the purchase allocation.
19.5 Frontend requirements
FR-UI-01: Users can connect a wallet.
FR-UI-02: Users can verify through World ID.
FR-UI-03: Users can link another wallet.
FR-UI-04: Users can view their allocation.
FR-UI-05: Users can view remaining spend.
FR-UI-06: Users can execute supported purchases.
FR-UI-07: Users can understand why a transaction was rejected.
FR-UI-08: Issuers can view and manage their offerings.
FR-UI-09: Users can browse offerings retrieved from Arkiv.
19.6 Arkiv requirements
FR-A-01: Issuers can publish offering metadata.
FR-A-02: The application can query offering metadata.
FR-A-03: The offering directory uses Arkiv data.
FR-A-04: The application validates enforceable policy information against the blockchain.
FR-A-05: Arkiv records have documented ownership and expiry.
FR-A-06: Arkiv failure does not disable onchain purchase enforcement.

20. Non-Functional Requirements
20.1 Security
* Critical purchase rules must be enforced onchain.
* Backend signing keys must remain private.
* Wallet registrations must be replay-protected.
* Trade authorizations must be replay-protected.
* The executor must authenticate the wallet and recipient.
* Policy updates must be permissioned.
* The system must not expose sensitive identity data.
20.2 Reliability
* Failed swaps must not consume allocation.
* Backend downtime must not corrupt onchain records.
* Arkiv downtime must not stop existing pools.
* The application must display stale-data warnings where appropriate.
* Contracts must have explicit emergency pause behavior.
20.3 Performance
* The purchase check should require a small number of predictable storage reads.
* The system should avoid unnecessary external API calls during swaps.
* World verification should happen before registration, not inside the swap.
* Arkiv queries should not occur during swap execution.
20.4 Usability
* The main investor flow should be understandable without blockchain expertise.
* Users must understand why World ID is required.
* Users must understand that linked wallets share an allocation.
* Users must see the remaining allocation before confirming a purchase.
* Error messages must explain what action the user can take.
20.5 Maintainability
* Contracts must have clear responsibilities.
* Backend endpoints must have documented request and response formats.
* The Arkiv schema must be documented.
* The repository must include setup instructions.
* Deployment addresses must be recorded.
* Tests must be reproducible.
20.6 Compatibility
The MVP targets:
* EVM-compatible network supported by the selected Uniswap v4 deployment.
* Compatible PoolManager and router infrastructure.
* USDC or a compatible six-decimal test token.
* EOA wallets initially.
* Modern desktop and mobile browsers.
The exact target chain and deployed Uniswap infrastructure must be confirmed before deployment.

Question
	Decision for V2 MVP
	Can one person link multiple wallets?
	Yes, through World ID session proofs.
	Does every wallet get a separate purchase limit?
	No. Linked wallets share one allocation.
	Is the World ID session ID stored onchain?
	No.
	Is the allocation identity the World ID nullifier?
	No. It is an opaque issuer-scoped application identifier.
	Can the same human have different allocations for different issuers?
	Yes.
	Does the system collect legal identity information?
	No.
	Does Proof of Human establish KYC?
	No.
	Can a user purchase without registration?
	No, through supported retail routes.
	Can a user use an unsupported router?
	No. The hook rejects unsupported routes.
	Can a user use exact-output swaps?
	Not in the MVP.
	Can a user use multiple quote tokens?
	Not in the MVP. USDC only.
	Does selling restore allocation?
	No.
	Does a failed swap consume allocation?
	No.
	Can multiple pools share an allocation?
	Yes, through a common allocation group.
	Can an issuer change the cap?
	Yes, with permission and versioning.
	Can a policy update reset spend?
	No.
	Can an issuer pause an offering?
	Yes.
	Does Arkiv enforce purchase limits?
	No. The contracts do.
	Does Arkiv store identity information?
	No.
	Does Arkiv failure stop swaps?
	No.
	Does the MVP prevent direct token transfers?
	No.
	Does the MVP enforce ownership across all chains?
	No.

	Not initially; EOA support first.

	No. It is optional.

32. Success Metrics
32.1 Core product success
The MVP succeeds if:
* One human can link at least two wallets.
* Both wallets share the same onchain spending counter.
* A purchase below the cap succeeds.
* A purchase above the cap is rejected.
* A different human has a separate counter.
* Two pools can share one allocation group.
* Failed transactions do not consume allocation.
32.2 Technical success
* All critical Foundry tests pass.
* Hook integration tests use a real PoolManager call path.
* Contract deployment is reproducible.
* The backend verifies World ID proofs.
* Session linking works.
* The frontend reads allocation data from chain.
* Arkiv writes and reads work on the current testnet.
32.3 Submission success
* Public repository.
* Clear architecture.
* Reproducible demo.
* Verified contracts where supported.
* Transaction hashes.
* Complete partner documentation.
* Clear differentiation from existing projects.

34. Final Product Definition
RWAComply V2 is a human-level allocation-control system for tokenized asset markets.
It uses World ID Proof of Human and session proofs to associate multiple wallets with one issuer-scoped allocation identity.
Issuers configure purchase limits and allocation groups.
A wallet linked to an allocation identity can trade through supported Uniswap v4 routes.
During each purchase, the RWAComply hook checks the shared cumulative spending record.
If the purchase would exceed the issuer's limit, the transaction reverts.
Arkiv provides a decentralized, queryable directory of public RWA offerings, while onchain contracts remain the authority for policy enforcement.
The MVP focuses on one clearly demonstrable capability:
A verified human cannot bypass an issuer's cumulative purchase limit simply by switching to another linked wallet.
That is the central product feature, the primary technical contribution and the main demonstration around which all other functionality should be built.
