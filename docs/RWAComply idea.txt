Brand Positioning 
RWAComply 
Building a Compliant Liquidity Layer for Tokenized Real-World Assets 
We position RWAComply as a specialized Uniswap v4 hook protocol that enables secure, 
adaptive liquidity pools for RWAs, bridging DeFi with regulated assets. This focuses the TAM on 
tokenized real estate, treasuries, and credit markets, with opportunities in institutional trading, 
retail access to RWAs, and cross-chain compliance automation. While platforms like Centrifuge 
focus on issuance and BlackRock on enterprise tokenization, adaptive, hook-native compliance 
for on-chain liquidity is underserved. We'll emphasize real-world utility in mitigating regulatory 
risks while unlocking DeFi composability for RWAs. 
Vision 
We're building a permissioned Uniswap v4 hook that creates tiered, compliant liquidity pools for 
RWAs (e.g., tokenized real estate or USDC-backed bonds). It gates access via KYC/identity 
checks and dynamically adapts parameters like fees or swap caps based on user tiers and 
oracle-fed real-world asset status. Integrated with Reactive Network for cross-chain reactivity 
(e.g., auto-updating compliance from Ethereum KYC events to Unichain pools), RWAComply 
supercharges Uniswap for institutions—delivering deeper liquidity, lower risks, and seamless 
DeFi integration without sacrificing speed. 
Problem Statement 
Regulatory Fragmentation in RWAs:  
Tokenized assets like treasuries face strict compliance hurdles, fragmenting liquidity across 
permissioned silos and deterring DeFi participation. 
Static Compliance Gaps:  
Existing hooks (e.g., basic whitelists) can't adapt to real-time events like asset audits or user tier 
changes, leading to over-exposure for retail or paused institutional flows. 
Cross-Chain Inefficiencies:  
Off-chain KYC or oracle updates don't propagate automatically, causing delays in volatile RWA 
markets and missed arbitrage opportunities. 
Our Customers 
Liquidity Providers (LPs) & Institutions 
Profile:  
Funds like BlackRock or retail whales providing liquidity to RWA pools (e.g., real estate tokens 
on Unichain). 
Pain Point:  
Risk of non-compliant flows eroding yields; need adaptive fees to protect against volatility 
without manual intervention. 
Willingness to Pay:  
Institutions allocate billions to compliant DeFi; they'd pay premium fees or protocol shares for 
risk-mitigated liquidity. 
Traders & Swappers 
Profile:  
Retail traders, algo bots, or enterprises swapping RWAs (e.g., converting tokenized bonds to 
stables). 
Pain Point:  
Blocked or capped access due to regs; lack of tiered execution leads to high slippage in 
low-liquidity pools. 
Willingness to Pay:  
Traders pay for better execution (e.g., lower fees via verification); integrate with wallets for 
seamless upgrades. 
RWA Issuers & Oracles 
Profile:  
Protocols like Centrifuge or Chainlink data providers feeding asset status. 
Pain Point:  
No native hooks to enforce real-world compliance on-chain, limiting adoption. 
Willingness to Pay:  
Low (integration fees); earn from boosted volume and protocol revenue shares. 
Workflow 
LP/Institution Workflow (Providing Compliant Liquidity) 
LPs are institutions or verified users supplying assets to RWA pools. 
1. Onboarding and Verification 
Connect wallet to the RWAComply frontend (Next.js dApp). 
Submit KYC via integrated identity (e.g., Circle or mock ENS merkle proofs) to get tier 
(retail/institutional). 
2. Adding Liquidity 
Select RWA pool (e.g., tokenized treasury/USDC on Unichain). 
Call beforeModifyPosition via hook—system checks tier and oracle (Chainlink for asset status); 
auto-adjusts range if under audit. 
Confirm: Hook mints NFT-wrapped position (for fractional yield accrual). 
3. Monitoring & Adaptation 
Dashboard tracks fees earned, tier upgrades (e.g., hold NFT to boost status). 
Reactive Network callback: On cross-chain event (e.g., KYC revocation on Base), auto-pauses 
position or hikes fees. 
4. Post-Provision 
Withdraw anytime; earnings auto-distributed minus compliance premiums. 
Trader/Swapper Workflow (Executing Compliant Trades) 
Traders are users swapping in/out of RWA pools. 
1. Onboarding and Verification 
Connect wallet to dApp. 
Optional: Verify for higher tier (unlocks lower fees/caps). 
2. Querying the Pool 
Input swap details (e.g., USDC to RWA bond). 
Hook's beforeSwap checks tier + oracle; applies dynamic fee (0.05% institutional vs. 0.5% retail) 
or caps size. 
3. Executing 
Approve: Transaction routes through hook on Unichain. 
Post-swap: afterSwap accrues fees to NFT for yield holders. 
4. Post-Trade 
Rate execution; track impact on pool health via dashboard. 
Differentiators 
Adaptive Intelligence:  
Unlike static permissioned hooks (e.g., VioletID gates), ours uses oracle + Reactive for real-time 
adaptation—e.g., auto-pause on "asset audit" signals, creating truly responsive liquidity. 
Cross-Chain Supercharge:  
Chatty oracles give snapshots; we enable event-driven callbacks (e.g., Ethereum KYC → 
Unichain update), reducing latency vs. manual bridges. 
Tiered Monetization:  
Basic hooks lack revenue loops; ours accrues fees to upgradable NFTs, turning compliance into 
a yield engine for LPs—while qualifying for Unichain/Reactive prizes via direct integrations.

High-Level How It Works 
Base Structure:  
Extend BaseHook from Uniswap v4-periphery. Deploy on Unichain testnet for demo. 
Key Callbacks: 
beforeSwap / beforeModifyPosition:  
Check user's compliance tier (e.g., via Circle Compliance Engine or a simple on-chain registry 
like ENS + merkle proofs for KYC). If low-tier, apply a higher fee (e.g., 0.5% vs 0.05% for 
institutions) or cap swap size. 
afterSwap:  
If integrated, accrue fees to an NFT (inspired by "NFT Strategy Token Hooks") representing 
fractional RWA yield—users "upgrade" tiers by holding it. 
Reactive Twist:  
Deploy RSC on Reactive Network to monitor an RWA oracle (e.g., Chainlink feed for asset 
status). On event (e.g., "compliance revoked"), it callbacks to your hook on Unichain to update 
the whitelist or pause. 
Oracle/Compliance:  
Use Chainlink for RWA data (e.g., tokenized real estate price feeds). For identity: Start with a 
mock registry (address list), upgrade to real like Worldcoin or Civic if time. 
Demo Flow:  
Video shows: 1) Unverified user blocked/capped. 2) Verified user swaps with low fees. 3) Oracle 
update triggers adaptive change (e.g., fee hike on volatility). Frontend: Basic Next.js app to 
interact (add liquidity, swap, check tier).

In the constructor, set up an Ownable pattern using OpenZeppelin for admin controls, and create a 
function to update user tiers based on mock KYC (e.g., admin adds addresses to a simple array or merkle 
tree for proofs). 
Add permissioned access gating in beforeSwap callback:  
Write the beforeSwap function to first verify the user's tier by checking against the registry; if unverified 
or low-tier, revert the transaction with a custom error message like "AccessDenied: Verify KYC for 
institutional tier". 
Incorporate dynamic fee adjustment in beforeSwap:  
Query the Chainlink oracle feed within beforeSwap to fetch the current RWA asset status (e.g., price 
deviation or audit flag); if volatility exceeds a threshold (e.g., 5%), apply a higher dynamic fee multiplier 
(e.g., 0.5% for retail vs. 0.05% for institutional) by returning a modified SwapConfig. 
Extend gating to beforeModifyPosition callback:  
Implement beforeModifyPosition similarly to beforeSwap, checking tier and oracle status before allowing 
liquidity adds or removals; for low-tier users during an "audit mode" signal from the oracle, cap the 
position size or auto-narrow the liquidity range. 
Accrue fees to NFT in afterSwap callback:  
Create an afterSwap function that calculates swap fees and transfers a portion to a linked NFT contract; 
emit an event for off-chain tracking to simulate yield accrual for fractional RWA positions. 
Design and deploy the NFT contract:  
Build a separate ComplianceNFT.sol as an ERC-721 contract using OpenZeppelin, with minting triggered

Install Chainlink contracts via Foundry (import from npm), configure the hook to use a specific feed (e.g.,

Set up mock identity registry for compliance:  
For MVP, implement a simple address-based whitelist in the hook contract; include a setter function for 
admins to add/remove addresses, and plan for future upgrades like ENS merkle proofs or Circle

- Run all tests:


```bash
forge test
```

```bash
forge test --match-path test/Counter.t.sol -vv
```

```bash
forge test --match-test <TEST_NAME> -vv
```
